## 2. 專案目標與開發原則

**目標**：在 Windows 上做一支自動操作短期（持有數天到數週）台股的程式，透過券商 API 下單，並有寫死在程式裡的風控與停機機制。先模擬、再小額實盤。

**專案目標（2026-10-08 使用者釐清）**：利用短期強勢股賺取價差，達到**小額獲利**。**不以贏過 0050 為目標，也不需要與 0050 比較**；0050 與全體等權、隨機挑選只用來辨識「賺的錢是不是只靠大盤上漲」，不是成敗標準。同時先驗證「這條自動化流程與風控能不能實現」；若回測顯示策略扣除成本後無法穩定獲利、或虧損無法控制在停機線內，可在早期階段停止，損失最小。

**開發原則（使用者要求）**
- 開發階段**不做 fallback 行為**：任何錯誤直接停止並顯示明確訊息，不悄悄略過、不自動重試、不截斷。
- 不算 fallback 的例外：斷點續傳（已有檔案就跳過）、避開已知的維護時段。
- 現況：新腳本（`download_pilot.py`、`announcements.py`、`init_db.py`）遵守此原則；`download_all.py` 依使用者指示保留舊行為（請求失敗就記錄、等待後略過、繼續下一個）。
- 回測與實盤使用同一種語言（Python），避免邏輯落差。
- 試的策略與參數組合越多，越容易碰巧過關；要記錄試過幾組。

## 5. 風控規則

### 已決定：總資金停機線（移動停機線）
- 記錄「收盤淨值的歷史最高點」，只升不降。
- 停機線 ＝ 歷史最高點 × (1 − 10%)。例：起始 20,000 → 停機線 18,000；最高點升到 23,000 → 停機線 20,700。
- 只在收盤後判斷（一天一次）。
- 觸發後：
  1. 停止所有新單
  2. 對現有持股送出賣單並通知
  3. **不自動恢復**，需手動確認才能重新啟動
- 歷史最高點必須存檔，程式重啟不可歸零；要重設只能手動。

### 已決定：單筆風險上限
- 單筆最多虧總資金的 **2%**（起始 2 萬元 ＝ 400 元）。
- 部位大小 ＝ 單筆風險金額 ÷ 停損幅度（例：停損 8% → 可買約 5,000 元）。
- 理由：同時持 3 檔且全數停損，合計約 6%，仍低於 10% 停機線，留有緩衝。

### 停損架構（方向已定，參數待回測校準）
三層，由內而外：
1. ATR 停損：停損距離 ＝ 若干倍 ATR（ATR ＝ 該股近期平均每日波動幅度），波動大的股票自動放寬
2. 移動停損：停損價隨最高價上調，只升不降
3. 硬上限：任何一筆虧損超過總資金 2% 就強制出場

### 尚未決定
- ATR 倍數、ATR 計算天數等具體參數（回測暫用 3 倍、14 日，見 9.2）
- 單日虧損上限
- 停機觸發是否要二次確認（避免單筆異常報價誤觸）
- 停機線 10% 是否合理：趨勢策略回撤 10% 可能很常見，需用回測的最大回撤分布校準，避免頻繁停機
- 觸發賣出時，盤中零股若只能掛當日限價單，急跌時可能賣不掉，需設計處理方式

### 要注意的限制
- 收盤才判斷停機線 → 盤中急跌要靠「單筆停損」那一層。
- 跌停鎖死、隔夜跳空、零股集合競價，都可能讓實際虧損超過停機線。
- 固定 10% 在本金變大後，能回吐的金額也會變大（目前起始 10% ＝ 2,000 元）。

## 6. 交易成本與零股規則

### 6.1 手續費與稅（回測採用的數字）
| 項目 | 數字 | 狀態 |
|---|---|---|
| 手續費費率 | 成交金額 × 0.1425% | 公定費率 |
| 電子下單折扣 | 3 折，採**月退佣**（次月折讓） | 使用者提供，2026-10-08 確認 |
| 最低手續費 | 盤中零股、盤後零股每筆各 **1 元** | 使用者提供；官網手續費計算頁寫「未滿 20 元以 20 元計」，與此不同，以使用者提供為準 |
| 證交稅 | 賣出時 0.3%（不打折） | 現股一般股票；ETF 與當沖不同，未查證 |

**尚未確認**
- 一張委託拆成多筆成交時，最低 1 元是否每筆各算（官網寫「單筆委託若有多個成交價，手續費分別計算」）。
- 月退佣下，最低 1 元是折讓前還是折讓後。
- 零股能否當沖、當沖證交稅是否減半（我印象有減半政策，但適用範圍與期限未查證）。

### 6.2 成本對策略的影響
- 以 5,000 元部位算，一買一賣約 19 元（3 折，約 0.39%）；不打折約 29 元（約 0.59%）。證交稅（0.3%）是主要部分。
- 成本是每筆固定的，所以每筆預期變動要夠大、交易次數要少。設平均獲利與虧損幅度都為 m、來回成本為 c，需要的勝率為：**勝率 > 0.5 ＋ c ÷ (2m)**。例：c ＝ 0.4%，m ＝ 1% 需約 52%；m ＝ 0.3%（盤中短線）需約 83%。
- 因此盤中短線（每筆變動 0.1～0.5%）很難覆蓋成本；多日持有（每筆變動 2～5%）成本占比低很多。
- 20 日突破回測中，手續費折扣影響很大：3 折時成本約吃掉全部毛利（見 9.3）。

### 6.3 零股交易規則（現況）

## 9. 策略與回測

### 9.1 策略方向
- 趨勢型；持有時間由訊號決定。具體進出場規則**尚未選定**。
- 第一個候選（9.2）是 20 日高點突破＋ ATR 停損，只是試跑假設。
- 第二個候選（9.5）：以籌碼與基本面特徵做多日持有的預測模型。
- 同日多檔出現訊號時需要明確的排序規則（只能持 1～3 檔）。

### 9.2 第一版回測：20 日突破（`src/backtest/donchian.py`）
以下數字皆為第一版假設，不是已決定的規則：

| 項目 | 假設 |
|---|---|
| 訊號 | 收盤價 > 前 20 日最高價，且近 20 日平均成交金額 ≥ 5,000 萬元 |
| 進場 | 隔天開盤價；同日多檔依近 60 日漲幅由高到低 |
| 停損 | 進場價 − 3 × ATR（14 日），隨最高收盤價上調（只升不降） |
| 出場 | 盤中最低價 ≤ 停損價，以 min(開盤價, 停損價) 成交 |
| 部位 | 單筆風險 2% 總資金 ÷ 停損距離；最多同時 3 檔；零股（1 股為單位） |
| 還原 | 除息、減資事件日之前的價格乘以調整係數 |
| 下市持股 | 主情境全損；對照情境按最後收盤價賣出 |
| 成本 | 手續費 3 折（對照：不打折），最低 1 元；賣出證交稅 0.3% |
| 參考對照 | 0050 買進持有（還原；只用來看大盤影響，不是成敗標準；2025-06 的 4 拆 1 暫用「單日跌幅 > 50%」偵測，之後改讀 SplitPrice） |

### 9.4 回測程式現況與限制
- 沒有逐筆核對交易明細，程式本身可能還有錯。
- 月退佣只當 3 折計算，沒有模擬先付全額再退；拆單成交的最低手續費沒有計入。
- 停機線只統計觸發次數，沒有真的停機。
- 樣本內（2005–2017）與樣本外（2018–）只是切分顯示，沒有調參，不是真正的樣本外檢驗。
- 流動性門檻（5,000 萬）是假設值。
- 其他個股的分割／面額變更尚未用事件表處理。

### 9.5 候選方向：多日持有的特徵模型（草案，尚未驗證）
- 動機：成本固定，要靠每筆預期變動夠大；盤中短線不划算（見 6.2），盤中個股歷史資料也不在免費清單（台新只有 1 個月）。
- 做法：用法人買賣、融資券變化、外資持股、借券、PER／PBR、月營收與價格動能等特徵，預測未來 5～20 日報酬；用走動式驗證，扣成本後看絕對報酬與回撤，並與全體等權、隨機挑選、簡單規則對照（辨識是否只靠大盤上漲）；使用梯度提升樹之類的傳統機器學習，不是讓語言模型每天判斷漲跌。
- 資料：先用 200 檔試跑資料（8.5）；有訊號才擴大到全市場。
- 要保留一段完全不碰的樣本外資料，並記錄試過幾組特徵與參數。
- 法人與融資券資料多在晚上 8、9 點發布，隔天開盤才能用，這是可用的最即時狀態。
- 不做 RAG：數值預測不需要向量檢索；「找相似歷史情境」用 SQL 事件統計或機器學習即可，且向量檢索更難察覺未來洩漏。

### 9.5.1 試驗紀錄（試的組合越多越容易碰巧過關，每次都要記錄）

**累計試驗次數：2**（試驗 #1、#2；皆未調參。另有 20 日突破回測的數次不同股票池與手續費情境重跑，見 9.3）

**試驗 #1（2026-10-08，`src/model/pilot_v1.py`，報告 `data/experiments/pilot_v1_report.txt`，預測 `pilot_v1_predictions.csv`）**
- **設計（事先固定）**：試跑 200 檔；決策日 t 收盤後，t+1 開盤進場、持有 10 個交易日、相對 0050 的超額報酬；21 個特徵（價格動能與波動、外資／投信買賣超占成交量、融資融券餘額占發行股數與 20 日變化、外資持股比例與變化、PER／PBR／殖利率、月營收年增率），每個決策日橫斷面排名；`HistGradientBoostingRegressor`（150 棵、深度 4、學習率 0.05、最小葉子 300，不調參）；標籤為超額報酬的橫斷面百分位；每月重訓，訓練標籤出場日早於決策日；測試期 2020-01 起，每 10 個交易日一個決策日（共 163 個，持有期不重疊，平均可交易 136 檔）；可交易需 20 日平均成交金額 ≥ 5,000 萬；下市無法出場計 −100%。
- **資料處理**：價格還原同時使用除息、減資、分割、面額變更事件（分割與面額變更為同一事件時只算一次）；0050 的 4 拆 1 已由分割表處理。調整後單日漲跌幅超過 30% 的次數為 4（尚未逐一檢視）。
- **結果（樣本外 2020-01～2026-10）**
  - **IC（模型分數與超額報酬的排名相關）平均 +0.056，t ＝ +4.3，61% 的決策日為正**；前段（2020～2024-06）+0.054、後段（2024-07 起）+0.059，兩段方向一致。
  - 前 20 名等權、扣成本後每期（10 個交易日）超額報酬（相對 0050）：3 折 −0.32%（t ＝ −1.3，年化約 −7.8%）、不打折 −0.52%（t ＝ −2.1）。毛超額約 +0.07%／期，成本以每期 100% 換手計（來回 0.39%）。實際相鄰兩期前 20 名只換手約 50%，若以此估成本約半，3 折下每期超額約 −0.12%（年化約 −3%，由已列結果推算，未重跑），仍為負。
  - 前 3 名等權：3 折 −0.33%（t ＝ −0.7）；相鄰兩期換手約 77%。
  - 動能（60 日）前 3 名：2020～2024-06 每期 +2.01%（t ＝ +1.97），2024-07 起 −1.04%（t ＝ −0.64）；前 20 名接近零。樣本內外不穩定。
  - 對照：隨機挑 20 檔每期超額 −0.59%（3 折），模型勝過 99% 的隨機組合；但 0050 在 2024-07 起平均每期 +1.76%，全體等權只有 +0.83%，所有組合在後段都輸 0050。
- **單因子診斷（只用來理解，不用來選特徵；測試期平均 IC）**：IC 主要來自**外資持股比例水準**（+0.058，t ＝ +4.4），其次殖利率（+0.042）、PER（−0.033，低 PER 較佳）、融資占比（−0.034）；法人買賣超與營收年增率的 IC 接近零（|IC| ≤ 0.02）。也就是說，訊號是「外資持股高的股票較強」這類慢變的水準特徵，不是短期資金流向。
- **絕對報酬（2026-10-08 補算，扣 3 折成本、每期 100% 換手、不含部位控制）**：前 20 名年化約 +20%、前 3 名約 +17%、全體等權約 +12%；最大回撤 26%／35%／31%；2022 年前 20 名 −20%、全體 −21%、前 3 名 −6%。其中約 +12% 是市場本身，模型貢獻約 +7～8%／年；回撤遠超過 10% 停機線。
- **解讀（推測，尚未驗證）**：排名上有統計上顯著的訊號，但幅度小；相對 0050 的超額報酬扣成本後為負（0050 僅作參考）。
- **要注意的限制**
  - **試跑股票池有偏誤**：200 檔以整段歷史成交金額挑選、僅含代號 1101～2520，外資持股高與流動性高的股票本來就在 2020 年後的 AI 行情中表現強；這可能讓「外資持股比例」的訊號被高估，也可能只是這個時期的結果。需要全市場資料與更早期的測試期來驗證。
  - 測試期只有 2020 年後約 6.7 年，且包含單一大行情。
  - 訓練標籤補價（出場日無價取之後 5 日內第一個）在極少數情況可能略超出決策日，影響很小。
  - 手續費採百分比近似，未模擬 2 萬元零股的整數股與最低手續費。
  - 組合最大回撤是 10 個交易日一期的等權組合，不是 2 萬元的實際淨值曲線。
- **下一步候選（尚未決定）**：(a) 降低換手（只在排名明顯變化時調整持股）並重算成本；(b) 擴大到全市場資料，驗證外資持股比例是否仍有效；(c) 在 2012 年以前（無法人資料）只用價格與基本面特徵測試較早期，檢查訊號是否跨時期穩定；(d) 逐一檢視價格調整後單日漲跌幅超過 30% 的 4 筆。

  - 實際零股滑價未知（待查證）。參考：股價 1,000 元以上最小升降單位 5 元（約 0.5%）、500～1,000 元為 1 元（0.1%～0.2%），高價股即使不滑價，買賣價差本身就接近這個量級。
- **對照階段 1 過關標準（9.6）**：絕對報酬 > 0（通過）；停機線平均每年 ≤ 1 次（3 折剛好 1.0 次、不打折 1.5 次未過），最大回撤 ≤ 10% 未過（25～36%）；交易筆數 ≥ 30（通過）；成本占毛利 ≤ 30～40%（3 折 39% 邊緣通過、不打折 44% 未過）；勝過隨機進場（通過）。
- **解讀（推測，尚未驗證）**：在這個股票池與期間，模型選股明顯優於同規則的隨機進場，且在零滑價下帳戶為正報酬；但回撤與停機頻率貼近或超出標準，成本占毛利接近上限；加入單邊 0.25% 的滑價後報酬大幅縮水、0.5% 約兩平。**優勢存在但很薄，每年約 72 筆交易的高換手讓它對成交品質極度敏感。**要能用，需要降低換手、提高每筆的預期獲利，或確認實際滑價遠低於 0.25%。
- **要注意的限制**
  - 股票池偏誤（見試驗 #1）；隨機對照也在同一個池中，所以「勝過隨機」排除了市場影響，但不能排除「模型偏好外資持股高的大型股、而這類股票在此期間表現較好」。
  - 只有一條路徑，結果對細節很敏感（見上）；未做 TOPN、持有天數、ATR 倍數的穩健性測試（這些若調整，試驗次數就要累加）。
  - 成交價用一般盤的開盤價（再套滑價敏感度）；實際零股盤中第一次撮合為 9:10（見 6.3），價格會不同；未模擬漲跌停與流動性衝擊。
  - 停機後「停手 20 個交易日再重啟」是我的假設，實際由人工決定。
  - 第一次執行發現停機重啟後高點未重設，導致每 20 天重複觸發停機（只剩 14 筆交易、觸發 81 次），已修正並重跑；以上結果為修正後。
- **下一步候選（尚未決定）**：(a) 穩健性：TOPN、持有天數、ATR 倍數、起始日位移各做小幅變動，看結果是否崩壞（每次都記入試驗次數）；(b) 擴大到全市場資料驗證股票池偏誤；(c) 降低換手以降低對滑價的敏感度（例如持有更久、只在分數明顯變化時換股、提高進場門檻），這是滑價分析之後最直接的方向；(d) 用 2012 年前（無法人資料）的期間檢查跨時期穩定性。

### 9.7 標的池與交易次數

**學到的事**
1. **成本門檻**：每筆來回約 0.4%（3 折、零滑價）～0.9%（單邊滑價 0.25%）；過去所有短線設定的每筆毛利只有零點幾個百分點，低於門檻。
2. **選股有優勢，但小於成本**：各設定都勝過同規則的隨機挑選，但差距不足以蓋過成本。
3. **高換手對成交品質極敏感**；固定小額停利（+2%）搭配寬停損，在勝率 63～67% 下每筆淨利仍為負。
4. **基礎設施可信**：全市場資料庫、還原價、注意與處置股歷史、帳戶模擬引擎（冒煙測試 43 項、情境測試 23 項、23 種植入錯誤全數抓出）、資料切分與試驗紀錄流程，都已就緒，可重複使用於任何新假設。
5. 開發期結果不代表「沒有任何方法可行」：只代表「草案基準規則、持有約 10 個交易日、2 萬元帳戶」這個組合在成本下沒有優勢。

**使用者決定（2026-10-09）**：不再往驗證期投入這組規則；**不放棄專案**。使用者的看法是：散戶難勝大戶、ETF 穩定是通則，但市場上仍有人靠股票獲利（可能是短期或長期），應該有專業人士使用而我們尚未測到的規則，值得有紀律地繼續找。

**需要同時記住的現實**：公開文獻（據我印象，未查證的台灣當沖研究）顯示多數當沖者虧損、持續獲利者極少；成功者的優勢常來自速度、資訊或資金規模。這不代表不可能，但表示「找到邊際」本身就是高難度、容易自欺的工作，所以方法上要以防止過擬合為優先。

### 9.10 候選假設與「訊號掃描」方法（草案，2026-10-09 討論）
**為什麼改用訊號掃描**：過去每個想法都要建完整的進出場規則再跑帳戶模擬，成本高、參數多，容易在調參中自欺。改為**先量化訊號本身的毛利**：條件成立後，從隔天開盤進場，持有 h 個交易日的平均超額報酬（相對當日全體平均）、事件數、顯著性，再與成本門檻比較；通過的才建規則做帳戶模擬。

**掃描設計（事前固定）**
- 期間：開發期 2007～2016 掃描；驗證期 2017～2021 只驗證通過者；最後測試期 2022 起保留，只跑一次。
- 持有期 h ∈ {5, 10, 20, 40, 60} 個交易日（含長一點的，因為成本固定、持有越久成本占比越低）。
- 指標：每個事件的毛超額報酬（%）、事件數、按日聚合的 t 值（同一天多個事件先平均，避免重複計算）。
- **多重檢定**：掃描的所有（訊號 × 持有期）組合都計入試驗次數，以 Benjamini-Hochberg 控制偽發現率（q < 0.10）；單看「最好的幾個」不算數。
- **進入帳戶模擬的條件**：扣除保守成本（單邊滑價 0.25%，來回約 0.9%）後平均超額報酬仍 > 0、通過多重檢定、事件數足夠（建議 ≥ 300）、報酬不集中在少數年份；仍需通過階段 1 標準與驗證期。
- 注意：「相對當日全體平均」排除大盤漲跌，但仍是只做多的設定；做空與放空不納入（零股無法融券）。

- **解讀**：(1) 毛利隨持有期拉長而增加（H4b：5 天 +0.14%、20 天 +1.14%、60 天 +2.63%），成本固定，所以長持有才有淨利；先前強勢股規則最多持有 10 天、均線跌破即出場並有 7% 停損，推測因此切掉了這個優勢（尚未驗證）。(2) 52 週新高（H4a、H4b）是同一個現象的兩種寫法，視為一個假設族；與文獻「52 週高價動能」的方向一致。(3) H8 短期反轉的毛利明顯，但對滑價敏感：單邊滑價從 0.25% 升到 0.5%，持有 5 天的淨利約從 +0.86% 降到 +0.36%，到 0.75% 約轉為負；且訊號每年約 830～940 次，需要排序規則才能在 3 檔限制下挑選。

- **下一步需要使用者決定**：(a) 長持有策略與規格的「單筆風險 2%」並存的方式——停損 15% 時 2% 風險只允許約 13% 資金（約 2,700 元）一檔，三檔只用 40% 資金；要放寬單筆風險，或用較小的停損，或改成不設個股停損、只靠停機線與分散；(b) 同日訊號多於空位時的排序規則；(c) 各族取哪一個代表規則做帳戶模擬（建議 H4b 持有 60 天、H4a 持有 60 天、H8 持有 5 天各一個，記 3 次正式試驗）。

## 10. AI 的角色與影子模式

### 10.1 原則
- AI **不負責**買賣決策、停損、停機；執行與風控維持寫死規則。
- 不用 AI 判斷做歷史回測：模型可能已知那段期間發生的事，會高估績效。
- AI 的價值放在：開發階段協助（寫程式、檢查未來洩漏、解讀結果）、文字資訊的結構化抽取（公告、新聞變成欄位）。
- 若要把 AI 的判斷用在訊號上，用「影子模式」（只記錄不下單）前瞻驗證，跑一兩個月再決定留不留。

### 10.2 為什麼不採用的做法（2026-10-08 討論結論）
- **看 K 線圖截圖判斷**：圖是價格數字的有損壓縮，沒有新增資訊；回測成本高；若要驗證可做小實驗（抽 500 個遮掉日期與代號的歷史時間點，與簡單規則比較準確率，約 10 美元），目前未做，我預期不會比簡單指標好。
- **盤中即時分析＋歷史模型**：盤中個股歷史資料不在免費清單；成本占比高（6.2）；與機構比速度沒有優勢。先驗證有歷史的資料（9.5），有訊號再考慮即時系統。
- **RAG**：見 9.5。

### 10.3 盤後公告影子模式（`src/shadow/announcements.py`）
- **來源**：證交所 OpenAPI `https://openapi.twse.com.tw/v1/opendata/t187ap04_L`（上市公司每日重大訊息）。**只回傳最近一個交易日，無法回補歷史**，所以每天都要跑，錯過的日子補不回來。上櫃公告在櫃買中心，尚未查。
- **欄位**：出表日期、發言日期、發言時間、公司代號、公司名稱、主旨、符合條款、事實發生日、說明；來源欄位名稱有多餘空白（如 `"主旨 "`），程式讀取後去除，原始檔保留原樣。
- **未確認**：公告範圍是否包含當天盤後發布的內容（2026-10-07 出表的資料，發言日期是 10/06、時間約 07:00）。需在傍晚再抓一次確認，這決定績效追蹤從哪天算起。
- **流程**：抓取 → 原樣存 `data/shadow/raw/<出表日期>.json` → 逐則呼叫 Claude → 存 `data/shadow/announcements/<日期>.json`（含模型、提示詞版本、token 用量、估算成本）。已有同日期結果就略過；要重跑須先手動刪除。
- **模型**：`claude-sonnet-5-5`，`effort: low`，用結構化輸出（`output_config.format` JSON schema）保證格式；非正常結束（stop_reason）直接報錯；**依「不做 fallback」原則，未啟用拒答備援**。
- **輸出欄位**：
  - `event_type`：財報營收、股利配息、增資減資、併購重組、重大契約訂單、人事異動、訴訟裁罰、取得處分資產、庫藏股、股權異動、更名面額、其他
  - `direction`：positive／negative／neutral（只依公告字面判斷，不足以判斷用 neutral）
  - `is_routine`：只有純程序性、不含新業績／股利／交易資訊的公告才為 true（法說會邀請、更正補正、催繳、股東會通知、媒體澄清、資金貸與背書保證的例行申報）
  - `summary`：繁體中文一句話；提示詞要求 ≤ 50 字，程式超過 100 字就報錯（結構化輸出無法限制長度；v1 實測模型約超出要求字數 20～40%）
- **提示詞版本**：v2（2026-10-08）。v1 把營收、股利類公告誤標為例行（28 則），v2 收緊定義後降為 10 則；同一天 54 則裡 24 則與 v1 不同，但兩版各只跑一次，輸出有隨機性，差異部分可能只是波動。v2 的方向判斷（如月損益、庫藏股屆滿標為正面）未逐則核對。
- **成本**：54 則共輸入 84,131／輸出 4,948 token，約 0.22 美元（Sonnet 5.5 牌價 2／10 美元每百萬 token 估算，未核對帳單）；每月約 5 美元，財報季會更高。
- **認證**：服務帳號金鑰，建立時選 30 天到期（約 2026-11-07，以 Console 為準，到期前會收到提醒信），放 `.env` 的 `ANTHROPIC_API_KEY`；到期前手動換新。評估過 Workload Identity Federation，結論是本機 Windows 沒有現成的身分提供者，要自己簽 JWT，等於把長期金鑰換成長期私鑰，複雜度高、收益有限，不採用。建議另在 Console 設定預算上限或用量提醒。

### 10.4 價值評估與成功標準（草案）
- **預期**：對獲利的幫助很小。公告是公開資訊，市場在公告當下就會反應；隔天開盤進場時通常已反映；AI 沒有額外資訊；成本壓力仍在。價值主要在：便宜地驗證這個問題、風險類事件標記（減資、暫停買賣、重大訴訟、下市相關）、測試流程。
- **樣本需求（估算）**：隔日報酬波動約 2～3%，要看出 0.5% 的超額報酬約需 100 筆以上事件；看 3～5 天報酬約需 400 筆以上；規則過濾後每天候選可能只有幾檔，需累積一到兩個月。切分越多組合，越容易碰巧看到好結果。
- **成功標準（草案，看結果前先定）**：候選股隔日開盤進場、持有 1／3／5 天，扣成本後超額報酬 > 0 且 t 值 > 2，樣本 ≥ 200 筆，並優於「同一天隨機挑選」的對照；同時追蹤風險類事件。最可能的結果是「沒有可用的選股訊號」，那也是有價值的結論。
- **尚未做**：規則過濾（成交量、處置／注意股、買不買得起、事件白名單）、1／3／5 天績效追蹤與對照、每日排程。

## 12. 階段 5：資料管線與監看 UI

### 12.1 資料管線（已決定方向）
- **架構**：Google Cloud 排程觸發雲端 Python 腳本，每日收盤後抓資料存進 Cloud Storage；交易核心在本機同步下載，並在本機運算。
- **原因**：資料管線一天只跑一次，不需要 24 小時開機的 Windows 主機；Core API 只支援 Windows，交易核心仍放在自己的專用 Windows 機器。
- **設計原則**
  - 盤中交易**不依賴雲端**：核心只讀本機副本；同步失敗就沿用最後一份，若資料不是最新交易日，**不開新倉**（只允許出場與風控）。
  - 檔案依日期分割，寫入完成後才更新「完成標記檔」（含日期、筆數、校驗碼），核心驗證通過才使用，避免讀到寫到一半或異常的檔案。
  - 原始價與除權息事件分開存，還原價在讀取時推算。
  - 管線要有交易日曆（含颱風假等臨時休市）、可重跑不重複、失敗時通知。
  - 雲端只放公開市場資料，**不放**券商帳密與憑證；本機讀取用唯讀權限的服務帳號。
  - 設定預算警示，避免意外計費。
  - 排程要避開 FinMind 週日 00:00～03:00 的維護時段（8.3）。
- 一次性回補好幾年的歷史資料：在本機跑完再上傳，不用雲端函式（可能超過執行時間）。
- 每日增量更新：免費方案需逐檔請求（見 8.3），需設計分批；全市場一次取得要付費。

### 12.2 監看 UI
- **原則**：交易核心與 UI 分離。UI 只負責顯示，核心掛掉不影響下單邏輯，UI 掛掉也不影響交易。
- **建議顯示**：目前淨值與歷史高點、停機線、持股與損益、當日委託與成交、風控狀態、最近 log、連線狀態。
- **建議操作**：只保留「手動緊急停機」，避免在 UI 上隨手下單。
- **形式（已決定，之後再做）**：靜態網頁，部署到 Firebase，跨裝置查看。
- **設計原則**
  - 交易核心先把狀態寫到本機（例如 SQLite 或 JSON），另有獨立的小程式負責同步到 Firebase，交易核心**不依賴網路**，Firebase 掛掉不能影響下單與風控。
  - 只同步摘要（淨值、高點、停機線、持股、風控狀態、心跳時間），**不放**券商帳密、憑證、API 金鑰、帳號。
  - 網頁必須登入驗證，並設定資料庫安全規則，只有你本人能讀。
  - 顯示「最後更新時間」，超過一定時間沒更新就標示異常，才分得出「沒變化」和「程式掛了」。
  - 更新頻率要考慮免費額度，不要每秒寫入；定期快照加上事件觸發即可。
  - 緊急停機若做成網頁按鈕：遠端通道**只允許觸發停機**，不允許下單、不允許恢復；恢復只能在交易主機上手動操作。

## 13. 營運注意事項

- 盤中電腦不能睡眠、不能自動更新重開機，最好用專用機器。
- 斷線處理：偵測到斷線就停手，重連後先核對委託狀態，避免重複下單。
- 同一價格或數量用兩種方式讀取，不一致就停機。
- 任何未知狀態（沒看過的錯誤、驗證失敗）一律停手並通知。
- log 要完整：每筆委託、成交、停損、停機都要記錄。
- 各項金鑰（FinMind、Anthropic）放 `.env`，定期輪替；Anthropic 金鑰 30 天到期，需記得換新。
